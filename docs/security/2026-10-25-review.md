# 2026-10-25 セキュリティ診断と対処

対象は現行Androidアプリ、ローカルTLSブリッジ、Web画面、今回変更したPC支援コード。ソース確認、隔離した実クラスの負例テスト、インストール済み端末での軽量な確認を実施した。侵入耐性や脆弱性ゼロを保証する診断ではない。

## 対処した問題

### 認証前の本文読み込みによる処理枠・メモリ占有

ブリッジは本文を読み終えてから認証していた。接続可能な相手が大きなContent-Lengthを宣言して本文を送らない場合、認証なしでメモリと限られたワーカーを占有し得る構造だった。情報漏えいや認証突破を確認したものではない。

ヘッダー段階でブリッジ／Webの認証とオリジンを確認し、未認証の保護API要求は本文を読み込まず拒否する。明示的なWeb登録・ペアリングには小さな本文だけを許可し、既存の端末側承認を維持する。重複・負数・不正なContent-Lengthと未対応のTransfer-Encodingも拒否する。ヘッダー待ち時間を制限し、認証済みの正規アップロードには従来の本文待ち時間を使用する。

隔離テストでは本文読み出しが呼ばれないこと、正規クライアントと登録が通ること、Web資格情報をブリッジ認証に流用できないことを検査した。実機でも100万バイト宣言のヘッダーだけを送り、認証なし・誤認証は401、別オリジンは403、正規の小さな合成要求は200だった。負荷攻撃や飽和試験は行っていない。

### 古いAndroidでの内部通知の送信元制限不足

Android 13以降はNOT_EXPORTEDを使用していたが、以前の動的受信登録には送信者権限がなかった。他アプリが内部用アクションを送って、ロキの再生停止や表情連動を誘発できる構造だった。機密情報送出やAI要求の実行を確認したものではない。

署名レベルの独自権限を宣言し、送信・受信の両側で使用する。Android 13以降のNOT_EXPORTEDも維持する。実機Android 12Lで、ロキへの権限付与、受信登録の要求権限、権限のない送信元の拒否を確認した。正規の内部送信と新しいOSの受信フラグは隔離テストで検査した。

この方式は[Android公式のブロードキャスト権限制限](https://developer.android.com/develop/background-work/background-tasks/broadcasts)に従う。Rokidからの装着通知は別の公開受信経路であり、内部通知の権限を適用して遮断することはしていない。

## 追加した防御と確認

- 一時画像のContentProviderでscheme、authority、パス段数を検証し、読み取りで内容が変わらず、明示した書き込みだけが切り詰めることを検査。読み取りによるデータ消失は再現せず、URI検証の追加として扱う。
- TLSの証明書ピンとトークンによる認証証明、誤証明書・誤証明拒否を確認。
- AES-GCMの往復、改変・誤鍵拒否、nonce、移行・保存制限を検査。
- ペアリングの無効・期限切れと並行要求、端末上の承認、Webの認証分離、CSP等の応答ヘッダーを確認。
- 現行の追跡対象テキスト1,145ファイルの指定パターン検索で、鍵らしい文字列の検出なし。追跡中の鍵コンテナファイルもなし。追加するファイルは公開前に別途検査する。値そのものを報告やログへ転記していない。
- ソースのアプリ設定はバックアップ無効、通常ビルドはdebuggable=false。開発APKと配布署名APKを区別する。

## 範囲外・残る確認

Git履歴全体、依存SDK・端末OSの全CVE、長時間の悪意ある通信、全端末での動作を網羅していない。既存の登録済み端末は許可した権限を持ち続ける。実移動・音声の体感・電池比較・固定版12時間試験は別の確認項目。公開APKv646/v288には本ページの追加対策は入っていない。
