# ナビの追加検証と修正（v633・v278）

## 追加した検証

操作検証を86から124ケースへ拡張し、最終実行では124成功・失敗0です。アプリの処理と実Androidダイアログを使用し、経路サービスと通信応答は合成データです。

- スマホ：徒歩・自転車・車・公共交通の候補選択→開始確認→開始、確認中/候補画面での取消。
- スマホ：登録区間の開始、連続決定、完了後の古い決定、応答喪失、取消後の遅延応答、検索条件変更、候補なし、取得失敗、新しい検索への切替。
- スマホ・メガネ：取得中・選択中・開始確認中の破棄処理。メガネは目的地入力画面の破棄も確認。
- 実Androidの検証ホストを取得中・選択中・開始確認中に再生成し、製品と同じ破棄ヘルパーが古いダイアログ/応答を残さないことを確認。利用者アプリ全体の画面再生成を再現したとの主張ではありません。
- 同時開始要求のclaim競合を20回確認。二つの操作主体が候補を置換した場合の古い候補拒否と、取消後の世代不一致も確認。これは共有状態部品の検証で、物理二端末間の同時操作の通し試験とは区別します。
- 既存のメガネ導線、定期受信との競合、登録地点、目的地/立ち寄り/別経路変更、乗降/休憩/到着操作も維持。

## 修正した製品コード

1. 画面破棄時に候補処理の世代を無効化し、取得・候補・確認ダイアログを終了。メガネは目的地入力ダイアログも終了。
2. スマホの検索中に目的地や移動手段が変わった場合、明示的に検索終了と再検索案内を表示。
3. 登録区間の開始確認を一度だけ受け付け、完了後の古いボタン処理も拒否。
4. 開始処理の応答不明時に「要求中」を残さず、現在の案内を確認し自動再送しない旨を表示。
5. 取消通知で先にダイアログが閉じられた場合も検索状態から取消を判定し、終了表示を更新。

検証のためスマホにもプロセス内だけの依存関係差し替えを用意しました。設定・Intent・HTTPで有効化する入口はなく、通常のアプリは既存の実処理を使います。

## 初回失敗の扱い

初回の追加検証は110成功・7失敗でした。取消の6件には、Androidが非同期に送る取消通知を検証側が待たず判定していた問題もあり、テストの待機を修正しています。古い応答の1件は、合成プロバイダが製品側と異なり古い候補を再公開する検証側の問題でした。検証側を修正した項目を製品の不具合件数に含めていません。上記の製品改善と、これら検証側の補正は区別しています。

## 全確認と呼べない範囲

実際の移動と聞こえる音声、位置権限の取消やOSのバックグラウンド制限、ロック画面をまたぐ利用者アプリ全体の動作、物理二端末の同時操作、外部経路サービスの全条件（終電・運休等）は今回の隔離操作検証だけでは合格にできません。複合ルートは既存の区間・状態遷移検証がありますが、実走の行き帰りを最後まで確認したものではありません。

外部API検証と端末更新の結果は別の証跡に記録します。未実行・接続待ちの項目を成功として扱いません。

## 実APIの確認

最大8回の許可に基づき、東京駅〜上野駅の公開座標間で検証しました。徒歩13ステップ・自転車12ステップ・車13ステップのGoogle経路を取得し、それぞれ全体形状を確認。公共交通は設定済みNAVITIMEで1候補を取得し、通常のアダプターで11ステップ（乗車1ステップ）・全体形状へ変換できました。道路接続の取得を含め呼び出し試行は6回。残る2回は使っていません。個人の現在地・自宅・勤務先は検索入力に使わず、案内は開始していません。

API検証後の全ファイル完全一致はfalseでした。導入時のバックアップからの追加照合では、変更は利用回数・接続/ヘルス時刻・通常の状態同期等にあり、目的地・移動手段の設定や認証情報に変更はありません。通常同期の暗号化workspaceファイルにも差分があり、検証後の全保存内容が同一とは扱いません。最新の状態を失うため、稼働中の状態ファイルを古いバックアップで上書きしていません。
