# Conversation media attachments (phone v203)

## Usage

- Phone: select up to six media items together (at most three videos) with **画像・動画を選ぶ**. Android 13+ uses the system Photo Picker; older systems and missing pickers fall back to Documents. Camera attachment is unchanged. The paste button reads clipboard image content URIs, not text or links.
- Google Photos: enable its cloud source in the system picker where supported, or select images in Google Photos and Share to Loki. Cloud downloads require connectivity. Loki requests access only to selected items, without requesting access to the entire photo library.
- PC/tablet Web: multiple file selection, image clipboard paste into the comment form, and file drop. Ordinary text paste and IME Enter behavior stay unchanged. Google Photos on desktop supports dragging a displayed image with its `lhN.googleusercontent.com` image URL (including the HTML image accompanying the page link). The authenticated phone API fetches and normalizes that selected image, then shows the attachment preview. No Google cookies or account credentials are copied. A page link without image data cannot resolve a private photo; opening the photo and dragging the image itself, or image clipboard paste, supplies the image.
- Video: add up to three local video files, each up to 120 seconds and 50 MB. Images and videos can be mixed, up to six attachments total. Supported formats depend on the Android/browser decoder. Eight equally spaced frames, with sample timestamps, are prepared locally. This is a **visual overview**, not exhaustive scene analysis or audio transcription. Short events between samples can be missed; attach specific frames separately when necessary. Meeting import remains the path for audio transcription.
- Selection prepares a preview only. Sending explicitly submits the prepared image to the existing Gemini image question flow. Follow-up questions and calendar review use the existing flow. This update does not upload original videos. Explicitly dropped Google Photos image URLs are fetched from Google’s image CDN before sending; analysis continues to use the existing Gemini API.

## Representation and limits

Multiple images are composed in numbered reading order into one JPEG overview. The same numbered overview is visible before sending. This retains the existing 600,000-byte attachment limit, 1 MiB HTTP body bound, encrypted 30-minute pending storage, request deduplication, and glass memory budget. It trades fine document detail for bounded memory; send detailed documents individually. New image and video selections append to the current attachments up to six total, at most three videos. Original normalized image parts are retained independently, so adding the second image rebuilds the overview with both images. Video and image attachments can be mixed. Clearing removes all attached parts. Failed native preparation preserves the previous attachment and its preview; failed Web preparation clears the preview and shows an error. No partial subset is sent silently.

Videos use only decoded visual frames; the title baked into the image explicitly says NO AUDIO. Image files are limited to 20 MB/80 million pixels each. Native URIs must be content URIs. HTML is parsed in an inert template without inserting it. Only explicitly dropped HTTPS `lhN.googleusercontent.com` image URLs can be fetched via the authenticated phone endpoint. No redirects, credentials, arbitrary ports, private addresses, or arbitrary URL proxying are allowed; content type, source size and pixel bounds are checked. Object URLs and bitmaps are released after preparation. Web preparation uses generation invalidation to prevent stale selection or logout from restoring attachments. An image attachment with an existing generated-media edit parent prompts the user to remove that parent, rather than silently ignoring the attachment.

## v201 drop visibility and browser flavors

Window capture listeners accept drops even outside the form or on a native file input. The visible drop target shows initialization, receipt, fetch and errors beside the attachment preview. DownloadURL, URL, text/x-moz-url, HTML src/srcset and bounded inline image data are handled in addition to files and URI lists. Unknown/empty payloads show their format names, never silently returning. A private device-local diagnostic stores only the latest timestamp, type names, file/image counts and stage; no signed image URLs, HTML, filenames or photo bytes are included.

## v202 / glass v552: sequential additions and independent coverage

Two separate Google Photos image drags previously replaced the first image with the second. Sequential image drags, file selections and image paste now append; the displayed total and numbered preview show what will be sent. Each original is normalized separately and cached, rather than adding an already combined overview as another image. Native encrypted drafts persist the original parts through activity recreation.

The real `imageCount` is sent from Web/native composer, persisted with the encrypted pending request, bound to deduplication checks, validated on the glasses, and supplied to the image analysis instruction. For multiple images the model must answer under image-number headings in reading order, keep unrelated subjects separate, and identify unreadable images instead of silently skipping them. Explicit requests about only a particular image take precedence. The per-request JPEG and HTTP body limits remain unchanged.

Browser tests require Node.js, the `playwright` package and an installed Chrome or Edge. Run `node tools/ImageQuestionWebTest.cjs` and `node tools/MediaAttachmentsBrowserTest.cjs`; set `LOKI_BROWSER_CHANNEL=msedge` to select Edge. Browser test HTTP endpoints are local stubs.

Verification: Edge test checks red and blue pixels in the two-image preview after two separate additions, and verifies submitted imageCount=2. Native real-device test checks sequential additions and encrypted draft restoration without enqueueing a question. Gemini 2.5 Flash was tested with a synthetic bus drawing plus a fictitious appointment card; both normal and reversed order produced separate correct descriptions. No user photos, saved conversation history or custom instructions were sent in these API tests. Evidence is stored locally under outputs/install-phone202/multi-image-synthetic-test.json in the maintenance workspace.

## v203 / glass v553: multiple video files

PC/tablet Web supports dropping multiple video files together or appending them one at a time. The phone picker/share path also supports multiple video URIs. Each video is converted locally to an independent eight-frame storyboard. Only bounded JPEG storyboards are retained; raw video files are not uploaded by this path. Video source limit: 50 MB and 120 seconds each; at most three videos/six total media items. The attachment list preserves order and identifies video vs image. Clear removes the full set.

Mixed composites use taller panels for video storyboards to avoid squeezing their eight frames into a small square. The glasses instructions explicitly distinguish frames within one video from separate videos, and prohibit inferring audio or claiming exhaustive playback. Scene extraction uses a small end margin; if an exact-near frame cannot be decoded, the nearest sync-frame request is tried and marked `~KEYFRAME`. Failure preserves the prior attachments instead of silently dropping the failed video or sending a subset.

Verified: real Edge decodes synthetic MP4, adds multiple videos sequentially, mixes an image, rejects a fourth video while preserving prior attachments, preserves media after corrupt-video failure, and submits a four-item count. Native phone instrumentation confirms two real MP4 URIs, actual eight-frame extraction, mixed third image, and encrypted draft restore including types/order. Synthetic MediaStore rows are removed after the test. No Gemini API requests were needed for these video-loading tests. Google Photos image URLs remain supported; a Google Photos page/poster drag is not an authenticated import of the original video file.
